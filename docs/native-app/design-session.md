# 原生桌面 App 设计访谈

日期：2026-10-26。采用 grill-with-docs，每次一个问题，连续编号；决定确认后即时记录。

确认方式：Q1–Q15 由用户逐项确认；用户随后授权“接下来所有问题都按你的推荐，记录下来”，因此 Q16 起采用推荐方案，不再逐题等待回答。以下是设计决定，不代表功能已经实现或技术条件已经验证。

## 文档边界

本目录记录新的 Swift 原生 macOS 方案。现有 `docs/interaction-design.md` 和根目录 `CONTEXT.md` 描述 Web 版本，不直接作为本方案的交互约束。
本目录 `CONTEXT.md` 只记录术语，本文件记录范围、决定和待确认问题。

## 用户提出的方向

- 语音为主要交互，尽量减少点击。
- Swift 原生 macOS App，使用单窗口；无内容卡片时初始内容区尺寸为 560 × 900 pt，屏幕不足时适配可用空间。
- 视觉参考 Rare UI 的背景、配色、字体排版与组件。
- 底层始终包含 Fluid Orb、对话记录、文件／麦克风／键盘图标按钮组。
- 3D 卡片堆叠是核心 UX；AI 可调整顺序、并列或沉浸展示，并控制窗口尺寸。
- 新指令与已有内容相关时可并列并扩大窗口；无关时旧卡片退场；语音可关闭全部内容卡片。
- 长期方向：对话按时间连续，底层 thread 在上下文容量需要时切换并交接；本轮范围及后续方向见 Q16、Q29。
- 本轮内容固定为 YouTube 视频 https://www.youtube.com/watch?v=nKVZBKoB6P4 和 X 首页 https://x.com/home 。

## 已确认决定

### Q1 — mock 的边界

选择 1：真实交互，固定内容。

- 原生窗口与卡片接入现有真实语音和 Agent。
- AI 解析口头指令，控制卡片、排列和窗口尺寸。
- 只固定视频与网页地址，本轮不实现搜索。
- 不采用纯模拟语音或模拟 AI 的交互原型。
- 自动 thread 切换与交接按 Q16 留到下一阶段。

### 与旧方案的差异

- 旧方案将对话作为可交换主次的卡片；新方向将其放在常驻底层。
- 旧方案最多一张普通卡片；新方向允许相关内容卡片并列。
- 旧方案底部为时间／总览／小球；新方向为文件／麦克风／键盘。
- 旧方案首版未开放沉浸；新方向包含沉浸展示，规则见 Q11–Q13。

### Q2 — AI 对卡片内容的控制范围

选择 A：控制卡片，并提供视频播放／暂停。

- AI 控制内容卡片打开、关闭、排列与沉浸展示，以及视频播放／暂停。
- X 是可登录、可手动浏览的真实网页。
- 本轮不实现 AI 读取、滚动、打开 X 帖子或执行账号操作。
- YouTube 播放和 X 登录的嵌入兼容性尚未实测。

### Q3 — 卡片退场后的状态

场景：视频播放到 03:20，用户切换到无关的 X 内容，随后要求回到视频。

选择 A：退场时暂停视频并保留进度；重新唤起后回到原进度，明确要求继续播放时才恢复播放。X 保留浏览位置；本轮保证本次 App 运行期间的状态保留。

跨 App 重启恢复状态未纳入已确认范围。

### Q4 — 用户明确要求并列时的优先级

场景：视频播放时，用户说“保留视频，同时打开 X”。本轮 AI 不读取 X 内容，不能据此可靠判断网页与视频的实际内容关联。

选择 A：明确的保留、并列或替换指令优先于 AI 的关联判断；未明确时，AI 根据对话意图判断，无法确定关联则替换旧卡片。

### Q5 — 两张内容卡片保留时的默认布局

选择 A：默认采用前后有层次的 3D 堆叠；用户明确要求同时观看、对照或并排时，展开为并列布局并按需扩大窗口。堆叠后方卡片的可见程度与操作规则见 Q8、Q10。

后方卡片仍在场，不属于 Q3 定义的退场。

### Q6 — 视频位于堆叠后方时的播放行为

场景：视频正在播放，用户说“保留视频，打开 X”，X 来到前方。

选择 A：视频保持原播放状态，不因堆叠顺序改变而暂停或恢复；明确暂停或视频退场时才暂停。

### Q7 — Joe 语音回复期间的视频声音

选择 A：Joe 播报时临时压低视频音量，播报结束或被打断后恢复原音量，不改变播放进度；期间用户主动调整音量或暂停、关闭卡片时，以用户最新操作为准。

补充确认：用户语音输入时暂停视频，避免视频声音干扰录入；此处沿用保留进度的暂停语义。语音输入导致的暂停优先于 Q6 的继续播放与 Q7 的压低音量，压低音量不得自行恢复已暂停的视频。

语音输入前的播放状态按 Q9 恢复。检测用户开始说话及避免视频声音触发检测仍需真实设备验证；暂停不代表已解决起始检测的回声问题。

### Q8 — 堆叠后方卡片的可见程度

选择 A：后方卡片缩小、轻微倾斜并向侧上方错开，露出可辨认内容；前方卡片保持正面以便阅读和操作。

具体角度、偏移和尺寸在视觉实现中验证，不在此阶段固定数值。

### Q9 — 用户语音输入暂停视频后的恢复时机

选择 A：语音输入及本轮 Joe 回复期间保持暂停；本轮交互结束后，仅在输入前正在播放、视频仍在场且用户没有要求暂停或关闭时自动恢复。用户打断 Joe 并继续说话时，继续暂停。

该自动恢复仅适用于语音输入引起的临时暂停，不覆盖 Q3 的退场暂停或用户主动暂停。Q7 仍适用于 Joe 开口时视频尚在播放的场景，不要求为压低音量而启动视频。

### Q10 — 堆叠后方卡片的手动操作

选择 A：点击后方卡片只将其带到前方，该次点击不触发网页链接或播放器控件；到前方后可正常操作。语音可直接控制后方视频播放／暂停，无需先切换位置。并列时两张卡片均可直接操作。

### Q11 — 沉浸模式中的常驻区域

用户要求底层始终包含 Fluid Orb、对话记录和输入按钮组；需区分始终保留与始终可见。

选择 A：沉浸卡片占据主要空间，底部仍显示小型 Orb 与输入按钮组；对话记录保留但暂时隐藏，退出沉浸后恢复。

### Q12 — 进入沉浸的触发方式

选择 A：用户表达“放大看”“专心看视频”等意图时，AI 进入沉浸；普通的“播放视频”只打开并播放，不自动进入沉浸。提供手动进入／退出入口作为补充。

### Q13 — 退出沉浸后的布局恢复

场景：视频与 X 并列，视频进入沉浸，随后用户说“退出沉浸”。

选择 A：恢复进入沉浸前的堆叠／并列布局、卡片顺序和窗口尺寸；期间已关闭的卡片不复活，用户主动调整过的窗口尺寸不被旧尺寸覆盖。

### Q14 — 全部内容卡片关闭后的窗口尺寸

选择 A：撤销为卡片展示而自动进行的窗口放大，恢复此前无卡片时的尺寸，首次为 560 × 900；若用户在此期间手动调整窗口尺寸，则保留用户的新尺寸。明确要求“恢复默认大小”时再回到 560 × 900。

### Q15 — 非沉浸状态下内容卡片与对话区的关系

选择 A：内容卡片浮在底层对话区上方，允许遮住部分历史；底部保留 Orb、最近一轮对话与输入按钮，关闭内容卡片后露出完整对话区。

本题只确定非沉浸布局，不改变 Q11 中沉浸时隐藏对话记录的规则。

### Q16 — 自动 thread 交接的本轮范围

采用推荐 A：本轮聚焦原生语音与卡片体验，自动 thread 交接留到下一阶段；当前不能据此宣称已实现无限连续上下文。

### Q17 — 原生客户端与现有服务的边界

采用推荐：Swift 原生客户端负责窗口、卡片、输入和音频协调，复用现有 Mastra 后端的 Agent、模型、语音供应商与存储。保留现有 Web 客户端，不在本轮重写后端。

本轮为本机开发实验，后端可独立启动；不以自包含安装包、签名、公证或上架作为交付条件。后端不可用时明确显示连接状态并提供重试，不生成模拟回答。

### Q18 — 原生 UI 与既有 Web 规则的关系

采用推荐：App 外壳、布局和控件使用 SwiftUI，窗口管理按需使用 AppKit，网页内容使用 WKWebView。不将整个 React 页面套入桌面窗口作为原生交付。

BoardUI、Tailwind、Motion 属于既有 Web 实现约束；原生部分采用对应的原生组件、样式与动画机制。紧凑布局、避免多重边框、禁止内阴影、简洁中文文案及无障碍要求继续适用。

### Q19 — Rare UI 与 Fluid Orb 的复用方式

采用推荐：以 Rare UI 作为视觉参照，在原生端整理并复用颜色、字体层级、间距、圆角与动效参数；不假定 Web 组件能直接作为 SwiftUI 组件使用。

优先复用仓库已有 Fluid Orb 视觉与状态映射。本轮允许 Orb 作为隔离的 Web 渲染视图嵌入原生界面，避免为验证交互立即重写着色器；页面和卡片外壳仍是原生实现。同一时刻仅一处 Orb 持续渲染。

Rare UI 的具体视觉参数、资源许可与原生字体可用性须在视觉实施前核对；当前尚未浏览和完成设计审计，不编造已核实的设计 token。

### Q20 — 卡片数量与重复打开

采用推荐：本轮最多两张内容卡片，YouTube 与 X 各一个实例。重复打开已有卡片时带到前方或恢复展示，不重建、不重置内容。关闭全部卡片只使内容卡片退场，不清空聊天、不关闭麦克风、不退出 App。

手动关闭与语音关闭采用相同规则；保留简洁的关闭、沉浸及退出入口作为语音之外的补充。

### Q21 — 窗口尺寸、位置与小屏幕

采用推荐：560 × 900 指窗口内容区的逻辑点尺寸，不含系统标题栏。自动调整限制在当前屏幕可用区域内，尽量保持窗口中心不变，必要时移动以避免超出屏幕。

堆叠优先使用紧凑窗口；并列按内容可读性扩大宽度，视频保持比例，网页优先保证可读宽度。尺寸数值由真实内容验证，不预设未经验证的宽屏尺寸。

屏幕无法容纳可读的并列布局时降级为堆叠，并简短告知；不得挤成无法操作的窄卡片。手动调整后不立即反向抢改尺寸，用户新的布局／缩放指令可再次触发自动调整。

### Q22 — 沉浸与新指令的关系

采用推荐：沉浸是在同一 App 窗口内突出内容，不自动切换 macOS 系统全屏。简单问答保持沉浸；明确要求打开另一内容时退出沉浸，并按 Q4、Q5 决定替换、堆叠或并列。

沉浸前仍在场的另一张卡片只是隐藏，不视为退场；视频是否播放仍由统一声音规则决定。退出沉浸恢复仍有效的布局，不召回已关闭的卡片。没有明确对象的“关闭这个”指当前前方或沉浸卡片；“全部关闭”指全部内容卡片。

### Q23 — 持续接听、静音与键盘输入

采用推荐：首次说明并请求麦克风权限，授权后持续接听，无需唤醒词；无权限时仍能使用文本。麦克风按钮只控制输入静音，不关闭 Joe 的语音回复。

键盘按钮展开／收起文本输入，打字本身不关闭麦克风；语音转写与文本草稿分开。明确提交的文字与语音都进入同一 Agent 指令路径，并可打断当前回答。

用户主动静音时不得自动重新开启。App 重启沿用最后的输入静音选择；首次默认启用须以完成权限授权为前提。

### Q24 — 语音与视频的协调优先级

采用推荐：开始检测到用户说话即暂停视频并中断 Joe 当前播报，不等待完整转写。输入前正在播放的状态仅用于本轮恢复判断，不覆盖之后的用户意图。

优先级：用户主动暂停／卡片退场 > 语音输入及本轮处理造成的临时暂停 > Joe 播报压低音量 > 普通播放。明确的“继续播放”在输入完成并解析后可解除临时暂停；若仍有 Joe 播报，则按 Q7 压低音量。

输入无有效文字时，确认输入结束后恢复原播放状态；请求失败或取消时，不无限等待，结束该轮后按 Q9 条件恢复。新一轮语音已经开始时，上一轮结束不能触发续播。

实现前必须验证扬声器场景的回声处理与用户起声检测。若视频声音导致频繁误触，明确列为验收阻塞；耳机或手动静音仅是临时使用方式，不冒充完成免点击语音体验。

### Q25 — 网页、登录与视频的真实边界

采用推荐：YouTube 使用可受控的官方嵌入播放方案作为首选，需验证指定视频可播放及播放／暂停／音量控制；X 加载真实首页，登录由用户在网页中完成。

登录状态通过平台持久化网页存储保留；不把凭据、Cookie 或 X 页面内容交给 Agent。阅读位置与播放进度仅保证本次运行期间恢复，与持久化登录状态区分。

普通导航优先留在当前网页卡片；登录弹窗与外链策略在兼容性验证中确认，遵循单主窗口目标，不自行绕过网站登录或嵌入限制。无法嵌入时显示真实错误与用户可选的浏览器入口，但外部打开不算内嵌卡片验收通过。

### Q26 — Agent 对界面的控制契约

采用推荐：Agent 输出受限、结构化的界面操作，客户端校验并执行：打开／关闭指定卡片、前置、堆叠／并列、进入／退出沉浸、窗口缩放、视频播放／暂停。

客户端提供当前在场卡片、布局、播放及窗口状态供 Agent 判断；不提供 X 网页正文。Agent 不生成任意可执行代码，不直接控制系统其他窗口或任意网址。

执行结果返回 Agent，成功后才宣称操作完成。连续指令采用最新有效意图，已取消轮次的迟到操作不能恢复卡片或播放。纯展示操作不逐次弹确认框。

### Q27 — 文件、设置及已有功能的范围

采用推荐：文件按钮沿用已有文本附件范围：UTF-8 .md／.txt，每轮最多五个，单文件不超过 1MB／60,000 字符；不新增图片理解或文件管理能力。

本轮不新增设置、天气、阅读、搜索等内容卡片。后端已有配置与能力继续可用，但不承诺本轮完成全部原生设置界面和所有 Web 功能迁移；必要配置沿用现有方式。模型或语音错误应可见，不能因没有设置卡片而静默失败。

### Q28 — 本轮对话历史与重启行为

采用推荐：同一用户的原生客户端持续使用当前会话，重启后恢复当前会话记录，不因关闭卡片或退出 App 新建 thread。历史可滚动查看，界面不提供以 thread 为中心的导航。

展示历史与模型实际上下文分开描述；本轮沿用现有后端召回机制，不能宣称模型记得全部历史。重启后默认无内容卡片、不自动播放视频，输入状态按 Q23 恢复。

### Q29 — 下一阶段的连续对话方向

采用推荐方向，本轮不实现：thread 是模型上下文分段；“交接到新窗口”解释为新的上下文窗口，不新建 macOS 窗口，也不中断用户看到的时间线。

在容量耗尽前预留回复与工具预算，由程序依据模型容量和用量触发交接，AI 负责摘要内容。摘要覆盖当前目标、未完成事项、用户偏好、关键事实与卡片状态；原始历史保留，可追溯。

交接成功后才切换活动 thread，失败则保留原分段和待处理输入，不丢消息、不重复执行卡片操作。阈值、摘要预算与恢复协议留到该阶段结合模型能力验证。

### Q30 — 动效、可访问性与可验证交付

采用推荐：堆叠、前置、并列、沉浸和窗口调整保持连续过渡；避免以截图替代可用的网页内容。后方卡片不可点击内部内容，动画结束前不产生误触。

遵循系统减少动态效果设置，提供键盘操作、按钮可访问名称与可辨认焦点；语音故障不应阻断手动操作。前后景和窗口缩小时按需降低渲染负担，避免同时运行多个 Orb。

先验证网页嵌入及语音／音频链路，再完成空间布局；交付以真实交互演示和状态规则测试为准，不以静态截图或模拟成功代替。

## 验收场景

1. 启动时只有底层 Orb、对话与输入按钮；默认内容区为 560 × 900 pt，小屏不超出可用区域。
2. 语音要求播放指定视频，真实播放；开始说话立即暂停，回答结束按条件恢复，用户主动暂停不会被覆盖。
3. “保留视频，打开 X”形成默认堆叠；X 在前、视频在后，点击后方只前置，不误点播放器。
4. “并排显示”展开两卡并调整窗口；小屏降级可用布局。手动窗口尺寸不被迟到操作覆盖。
5. 不相关内容请求替换旧卡；回到旧视频恢复进度但不自动播放，X 在本次运行内恢复浏览位置。
6. “放大看”进入沉浸，保留小型 Orb 和输入按钮；退出恢复有效布局，不复活已关闭卡片。
7. “关闭全部卡片”暂停视频并清空在场内容卡片，露出完整对话区，持续接听不受影响，尺寸按 Q14 恢复。
8. X 能在卡片内真实登录与手动浏览；指定 YouTube 视频能真实嵌入与受控播放，失败时不宣称成功。
9. 验证拒绝麦克风权限、网络／后端失败、无有效转写、连续打断和迟到响应；输入不丢失，卡片与视频不意外恢复。
10. 验证重启恢复当前对话与登录状态，默认不恢复内容卡片、不自动播放；不将此验收解释为自动 thread 交接。
