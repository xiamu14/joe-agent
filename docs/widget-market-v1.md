# Widget Market V1

日期：2026-10-31。状态：已确认方案，尚未实现。协议依据：[Widget Unified Protocol V1](./widget-unified-protocol-v1.md)、[UI 协议](./widget-unified-protocol-v1-ui.md)。

## 1. 目标与已确认选择

提供第三方 Widget 展示、开发者注册、开发指导、网页一键发布和可信安装入口。开发指导主要通过官方 AI Skill、CLI、schema 与参考示例完成。

- 使用 GitHub App 提供 GitHub 登录、指定仓库授权和发布编排。
- 在开发者仓库的 GitHub Actions 中验证、构建和签名。
- 使用 GitHub Releases 分发不可变版本及签名证明，不自建文件分发 Registry。
- 自建市场网站、薄后端与可信 Catalog，维护发布者/Widget 归属、允许的签名身份、认可版本和撤回状态。
- 开发者签名必选：接受开发者明确授权的 CI 发布身份签名，不要求每次在浏览器中使用个人长期私钥签署。
- 市场与用户 Joe backend 独立验签，不能只依赖网页上的签名标记。
- 市场不托管用户的 Joe 记忆或 Widget 业务数据，不参与日常业务调用。
- 压缩算法、扩展名、安装包目录及签名文件的最终封装形式仍待讨论；本方案只依赖不可变产物、发布声明和摘要，不冻结打包格式。

## 2. 总体架构

```text
开发者 → GitHub 登录 → 市场网站
                        ↓
                薄后端 / GitHub App
                        ↓ 触发已授权的发布工作流
                 开发者 GitHub 仓库
                        ↓ Actions：验证、构建、签名
                GitHub Immutable Release
                        ↓ 独立检查、审核
               官方 Catalog 与签名元数据
                        ↓
               市场网站 / 文档 / AI Skill
                        ↓ 安装引用
               用户 Joe backend 独立验证
                        ↓ 权限确认与连接配置
                   安装 / 更新
```

市场账号和 Joe 用户身份不要求属于同一个账号体系。网站发布权限不等于访问任何用户 Joe 的权限。

GitHub 负责账号基础、仓库、CI、附件发布和下载；Joe 负责协议验证、签名授权策略、目录审核和安装运行安全。网站可以静态生成浏览页面，发布编排仍需要薄后端，不能把 App 密钥或 GitHub token 放入浏览器。

## 3. 产品区域

| 区域 | 首期功能 |
| --- | --- |
| 市场 | 浏览、搜索、分类、详情、版本记录、安装入口 |
| 开发 | GitHub 登录、发布者登记、仓库连接、Widget 管理、发布状态与审核结果 |
| 文档 | 统一协议、UI 目录、能力接口、数据/权限示例、AI Skill 和发布指南 |
| 管理 | 发布者/签名身份审核、候选版本审核、举报、撤回和审计 |

详情页展示名称、用途、截图、发布者、版本、兼容能力、必需/可选权限、域名、外部账号或费用要求、采集/外传说明、更新记录和支持链接。

“签名有效”“身份已验证”“审核通过”分别呈现，不能互相替代。签名不是安全保证，第三方 Provider 的远端代码也不因交付物签名而固定。

UI 菜单和动作使用简短日常中文，如“市场”“开发”“文档”“发布”“版本”“撤回”。授权与变更摘要必须准确，不为减少文字隐藏权限信息。

## 4. 账号、发布者和所有权

| 实体 | 语义 |
| --- | --- |
| 开发者账号 | 网站登录主体，关联稳定 GitHub 用户 ID |
| 发布者 | 个人或组织，拥有稳定发布者 ID 与 Widget 命名空间 |
| 成员角色 | 管理、开发、发布；最小权限授予 |
| Widget | 稳定 widgetId，绑定发布者，不随展示名称变化 |
| 签名授权 | 允许为指定发布者/Widget 发布的身份、仓库与工作流约束 |
| 发布版本 | 不可变产物、声明、证明及审核状态 |

GitHub 用户名、组织名和仓库路径仅用于展示与定位，不能作为唯一归属依据；保存稳定账号/仓库 ID，仓库转移、更名、发布者转移和签名身份变化须重新核验授权关系。

登录、仓库安装授权、Widget 发布资格和产物签名是四个独立检查。组织仓库需要管理员批准时保留其审批，不由网站绕过。

## 5. 首次配置与网页发布

首次配置：

1. GitHub 登录市场，建立发布者资料并验证命名空间归属。
2. 将 GitHub App 安装到开发者选择的仓库，不默认要求全部仓库。
3. 从官方模板创建项目，或由开发者合入官方发布工作流。修改工作流所需授权与触发工作流权限分开，首期不默认请求全仓库写权限。
4. 绑定 Widget、仓库及获准签名工作流；配置组织审批与发布策略。
5. 检查工作流、协议版本和不可变 Release 设置，显示可发布状态。

后续网页发布：选择 Widget、版本和具体提交，展示更新说明、权限/域名变化及签名身份，然后点击“发布”。后台核验用户当前权限，不因曾经登录或 App 仍安装就认定用户可以发布。

```text
创建幂等发布请求
→ 固定提交 SHA、版本、Widget 与发布请求 ID
→ workflow_dispatch
→ 校验
→ 构建产物
→ 签署发布声明
→ 上传草稿 Release 的全部附件
→ 正式发布不可变 Release
→ 市场独立验证
→ 待审核 / 已上架
```

工作流入口选择受保护 ref；实际 checkout 明确绑定已批准提交 SHA，不能让移动分支改变本次内容。工作流版本和依赖也须受控。具体工作流策略与证书可验证字段在实现时固定并通过集成测试验证。

发布请求 ID 在重试中复用；重复点击不能重复创建版本。版本唯一约束由目录与发布编排共同检查。同版本不同产物拒绝，修复必须升版本。

网页显示校验中、构建中、签名中、发布中、待审核、已上架或失败。GitHub 发布成功不等于市场上架成功；人工审核或 GitHub Environment 审批存在时，流程停留在相应等待状态，不假装即时完成。

## 6. GitHub App 与薄后端

GitHub App 可以分别代表应用、安装或用户调用 API。用户点击发布优先使用 GitHub App 用户访问令牌，保留用户和 App 权限的交集；后台安装令牌仅用于明确授权的自动任务，不能代替用户发布资格检查。

建议权限按用途划分：

| 用途 | 最小范围原则 |
| --- | --- |
| 登录 | 用户身份与建立会话所需信息 |
| 发现仓库/读取清单 | 选定仓库的必要读取权限 |
| 触发和查询发布 | Actions 写/读权限 |
| CI 创建 Release | 工作流自身受限 GITHUB_TOKEN 的 Contents 写权限 |
| CI Sigstore 签名 | 仅签名任务的 id-token: write |
| 官方目录更新 | 独立官方身份，只写 Catalog，不授予开发者构建任务 |

具体 GitHub 权限名和 token 可用范围在实施时对照对应 API 核验；不要为了方便申请全局 PAT。工作流配置变更若需要额外权限，应独立授权或由开发者手工合入。

薄后端负责 OAuth 回调、会话/CSRF 防护、令牌保护、安装绑定、权限核验、发布请求、工作流状态和 Catalog 审核编排。可使用托管数据库和任务队列，不需要自建 Registry。

webhook 必须验证签名，按 delivery ID 去重；异步事件可能乱序、重复或缺失，通过查询 GitHub 对账恢复。发布请求与 run/attempt/Release/产物绑定，不能将无关工作流成功误记为发布成功。

App 私钥是平台 GitHub 访问凭据，不是 Widget 开发者签名私钥。所有长期密钥与 token 留在服务端秘密存储，客户端只持有安全网站会话。

## 7. 必选开发者签名

采用 GitHub Actions OIDC + Sigstore/Cosign 身份签名。开发者授权的 CI 工作流取得短期身份，签署发布声明并输出验证 bundle，包含验证所需的签名/证书/透明日志证明。

无需开发者向网站上传长期私钥，也不要求平台代持开发者发布私钥。签名准确含义为“获准的开发者发布身份签署了该版本”，不是证明某个自然人逐次亲手签署。

发布声明至少绑定：声明类型和格式版本、发布者 ID、widgetId、Widget 版本、产物摘要算法/摘要/字节大小、manifest 摘要、来源提交与发布请求 ID。准确字节序列和序列化规则在契约阶段冻结，使用成熟签名实现，不自研算法。

manifest 及产物覆盖权限、域名、UI 和操作定义，改动后必须重新签署。构建后只签一次确定的产物；市场不得重新打包或修改后沿用原签名。最终签名与压缩封装方式待讨论。

验证不能仅检查密码学有效，还必须匹配签发方、获准签名身份、仓库/工作流策略、Widget 所有权、版本和摘要。声明里的自报身份不构成证明；使用证书、可信 provenance 和独立授权记录交叉核验。

官方 reusable workflow/Actions 固定可信版本，构建与签名发布分离。签名任务仅消费校验后的产物，不执行贡献者提供的任意脚本。不为普通 PR 或 fork 运行暴露正式签名/发布权限。

## 8. 三层信任与可信 Catalog

| 层 | 证明 |
| --- | --- |
| GitHub Release attestation | 产物与对应 GitHub 发布、tag、commit 的关联 |
| 开发者签名 | 获准发布身份认可指定 Widget 产物 |
| 市场签名元数据 | 平台认可的发布者/签名授权、分发版本及撤回状态 |

三层职责不同，GitHub Release 标记不代替 Joe 安装器验签。普通网站搜索索引可静态生成，安装信任信息必须具有独立可验证的签名与新鲜度策略。

Catalog 使用官方 Git 仓库维护，记录发布者、Widget、版本、产物摘要/大小/定位、签名证明引用、兼容性、权限摘要、审核和撤回状态。网站流程自动生成目录变更或 PR，开发者不必手工提交；审核通过后由独立官方任务生成索引。

建议复用 TUF 管理市场信任根、元数据版本、有效期和防回滚，不自建密码学更新协议。签名元数据可静态分发，不要求常驻 TUF 服务。具体库、角色和根密钥保管方式在实现阶段评估。

普通 PR 校验任务无官方签名/发布凭据，不 checkout 并执行贡献者代码来更新目录。官方索引签署任务与不可信产物检查隔离。

## 9. 检查、审核、更新与撤回

自动检查包括签名/身份授权、摘要、协议/schema、UI 目录和绑定、能力兼容、权限/域名、禁止代码、资源限制和必要的契约测试。压缩相关检查在格式冻结后补充，不在本文件提前确定格式。

首期采用自动检查加必要人工审核；未来低风险版本是否自动上架另定策略。测试使用隔离数据和测试连接，不能使用平台生产凭据验证任意开发者请求。

正常签名身份轮换应保留可验证历史，不无故使旧版本全部失效；密钥/身份失陷记录影响范围并撤销相应信任。发布者转移或签名身份变更需独立审核与审计。

撤回版本发布签名状态更新，不覆盖旧版本内容；决定禁止新安装、停止更新或停用已安装版本的严重性策略须明确。新安装/更新无法取得有效信任信息时拒绝继续；已安装离线运行策略在客户端实现前冻结。

市场审核通过不替用户授予权限。新域名、权限、外传范围或不兼容 schema 更新需要用户 Joe 重新检查。

## 10. Joe 安装边界

```text
市场安装入口
→ Joe 接收可信 Widget/版本引用
→ 获取可信目录及当前撤回状态
→ 下载确定产物和签名证明
→ 独立验证身份、摘要、签名、兼容性
→ 展示权限与连接配置
→ 用户批准
→ 原子安装并绑定唯一数据空间
```

市场链接不能直接获得本地 backend 控制权或完成用户授权。局域网、自部署、云端 Joe 使用同样验证器；公开市场不要求最终用户为下载公开版本提供开发者 GitHub token。

同 widgetId 更新保留原空间；删除重建遵循统一协议。下载失败、签名错误或安装不完整保留已有版本。禁止只信任可变 latest 地址，以目录固定的版本、摘要和引用安装。

## 11. AI Skill、文档与工具

官方 Skill 负责引导需求分析、查询匹配协议/组件目录、生成声明、配置 HTTP/MCP/存储、验证预览、形成候选版本和发布。Skill 不持有开发者凭据，不把签名秘密写入项目或提示词。

协议 schema、组件目录和操作契约是单一事实来源，生成版本化文档、示例与机器可读索引；Skill 引用对应版本，不复制一份容易过时的完整协议。

CLI/官方 Action 提供创建、校验、预览、测试、构建产物、签名与发布职责，具体命令名称待冻结。提供视频 Widget 全链路参考和失败场景，不只提供静态展示示例。

网页发布和 AI/CLI 发布进入同一校验、签名授权和 Catalog 流程。未签名草稿仅能受限开发预览，不能绕过正式分发签名要求。

## 12. 首期实施顺序与验收

| 阶段 | 交付 |
| --- | --- |
| M0 发布契约 | 发布声明、身份授权、版本唯一、目录 schema；等待产物格式确定后冻结封装 |
| M1 开发工具 | 协议校验器、视频示例、Skill、预览及测试入口 |
| M2 GitHub 接入 | 登录、选仓授权、角色检查、稳定身份与工作流配置 |
| M3 发布流水线 | 固定提交、校验构建、OIDC 签名、不可变 Release、幂等与状态回传 |
| M4 目录与网站 | 独立验签、审核、签名目录、浏览/详情/开发页面 |
| M5 安装闭环 | Joe 独立验证、用户授权、更新/撤回与故障恢复 |

验收覆盖：未授权用户不能发布；有效但不属于该 Widget 的签名拒绝；改动产物/manifest 后拒绝；同版本不能替换；重复点击不重复发布；移动分支不改变已确认提交；伪造/重复 webhook 不污染状态；GitHub 发布成功但审核失败不显示已上架；下载端不信任单纯网页标记；权限变化必须重新确认；App 卸载或用户失权后阻止新发布。

首次授权或组织审批不可消除；Actions 配额、平台故障、仓库/Release 删除会影响可用性。不可变 Release 不保证永远可下载。后续需要时增加按摘要镜像/缓存，不在首期自建 Registry。

暂不实现支付、评分推荐、私有市场、多 Registry 联邦、任意代码托管及用户 Joe 数据同步。压缩格式、签名封装、具体权限配置、审核自动化门槛及离线撤回策略仍需后续细化。
